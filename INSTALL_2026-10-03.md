Сначала прочитайте раздел «Что осталось» в `KAPANI_FIX_REPORT_2026-10-03.md`. Это архив изменений, а не подтверждённый production-релиз всего сайта. Особенно важно проверить оставшиеся клиентские финансовые операции со строгими правилами.

## 1. Проверить изменения

```bash

```

Результат при подготовке архива: 47/47. Для правил используйте Firebase Emulator или отдельную staging-базу; их компиляция/permission-сценарии не проверялись здесь.

## 2. Обновить canonical Worker

При наличии установленного Wrangler, из каталога `push-worker`:

```bash
wrangler deploy
```

Деплой должен выполняться из **полного дерева проекта**, поскольку `worker.js` импортирует `../functions/subscription-config.js`. Bindings/cron в `wrangler.toml` сохранены. Приватный VAPID-ключ и service account не включены в исправления; используйте уже настроенные secrets. Public VAPID-ключ оставлен прежним.

Если обновляете через веб-редактор Cloudflare, используйте готовый **`push-worker/worker-bundled.js`**: это та же реализация с встроенным каталогом, без относительного import. Он собирается командой:

```bash
node push-worker/build-dashboard.mjs
```

Не используйте `cloudflare-worker/worker.js` или исторические `kapani orig*.zip`.

Первое обращение к реестру устройств атомарно импортирует старый KV `subs` в закрытый RTDB `pushDevices`. Новые регистрации меняют RTDB с CAS, KV становится только источником первоначального переноса.

## 3. Отключить старые deployed Firebase push-функции

В исходниках их exports сняты, но это **не удаляет уже опубликованные функции**. Если такие функции существуют в проекте, отключите/удалите только старые push endpoints/triggers:

- `deliverKapaniWebPush`, `notifyOnChatMessage`, `notifyOnNewsCreated`, `notifyOnLegacyDuelNotification`;
- `createKapaniNotification`, `registerWebPushSubscription`, `updateWebPushPreferences`, `unregisterWebPushSubscription`, `getPushDiagnostics`;
- старую `giftSubscription`, поскольку подарок теперь обслуживает Worker.

Экономические функции `transferMoney/createOrder/payOrder/...` не удалялись. Не удаляйте их вместе со старым push. На Spark действующий push не требует Firebase Functions.

## 4. Правила и сайт

`firebase.json` теперь содержит `database.rules.json`. После проверки правил и совместимости старых финансовых сценариев публикация правил выполняется из корня:

```bash
firebase deploy --only database --project kapanisite
```

Это инструкция; в рамках подготовки архива команда не выполнялась. Не заменяйте production-правила вслепую: старые финансовые части ещё используют прямую запись клиента.

Обновите минимум `index.html`, `config.js`, `firebase-messaging-sw.js`, `functions/subscription-config.js` на текущем хостинге сайта. Новый build в профиле: `2026-10-03-canonical-push`. Service Worker: `kapani-webpush-2026-10-03-v5`.

## 5. Проверить на реальных устройствах

1. Выйти/войти после обновления, проверить вход старым паролем. Администратор получает новый signed custom token с admin claim только для существующего аккаунта `Денис` (или настроенного `ADMIN_NICK`).
2. В профиле включить push на двух устройствах; выполнить `await kapaniPushDoctor()` и `await kapaniPushSelfTest()`.
3. A отправляет B ЛС, сообщение чата и новость: проверить in-site и OS показ ровно один раз, затем повторить с закрытым приложением B.
4. Удалить уведомление, дождаться cron, перезайти: оно не должно возвращаться.
5. Проверить подарок без подписки, с истёкшей, продление того же уровня, upgrade и запрещённый downgrade.
6. Создать товар/бизнес без точки (запрет), с геолокацией и через карту. Для старого объявления добавить адрес из карточки.
7. Оформить доставку: подтвердить обе точки и цену; проверить баланс, резерв, seller credit, курьера, оба подтверждения и одну выплату. Изменить адрес товара после заказа — старый заказ сохраняет обе прежние точки.
8. Отдельно проверить банк, игры, аренду, обычную покупку при встрече, такси и остальные старые финансовые сценарии. Их серверная миграция не закончена этим архивом.
